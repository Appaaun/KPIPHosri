# Deployment — Ubuntu hospital intranet

Install a supported Ubuntu Server, Docker Engine and Compose v2 from approved sources. Restrict inbound firewall access to SSH administration and hospital HTTPS clients. PostgreSQL and Node ports remain loopback/internal; do not expose them publicly. Configure DNS and hospital-approved TLS, plus the optional Nginx location snippet in docker/nginx.conf. Set matching HTTPS APP_URL and NEXTAUTH_URL. Forward Host/protocol correctly. Production cookies require HTTPS.

Copy .env.example into a protected ignored .env; generate unique AUTH_SECRET and database credentials securely. No default passwords. Disable SEED_DEMO_USERS and SEED_DEMO_DATA. Use separate restricted runtime and migration DB accounts in production (the single Compose bootstrap account is a local simplification). Never put HIMPRO credentials into browser variables or source metadata. Use disk encryption and host patching.

Run `docker compose up --build -d`. Migration service waits for PostgreSQL health and deploys migrations before web/worker start. Initialize departments/settings with `docker compose run --rm web npm run db:seed`. Create the first administrator using securely supplied ADMIN_EMAIL/ADMIN_USERNAME/ADMIN_PASSWORD and `docker compose run --rm -e ADMIN_EMAIL -e ADMIN_USERNAME -e ADMIN_PASSWORD web npm run admin:create`. Disable bootstrap credential injection afterward. Health endpoint `/api/health` checks database connectivity without revealing configuration.

Set container log rotation (provided 10 MB × 3 files); configure equivalent Nginx/host rotation. Back up daily, test restoration regularly and before upgrades. Pin deployment image digests after acceptance. Before upgrades: backup, stage migrations and workflows, build/version images, deploy migrations, then roll out web/worker. Additive migrations are preferred. Rollback uses the prior image only if schema remains compatible; otherwise restore the verified backup into a separate DB during a planned outage. Never assume destructive migrations can be reversed automatically. Run security/dependency review and restore/load tests before real hospital use.

## Building inside Codex cloud

The cloud's proxy hostname and CA are not automatically available inside Docker build containers. `sh scripts/cloud-docker-build.sh` resolves the existing proxy locally, passes Docker's standard proxy build arguments, and mounts the provided public CA as an ephemeral BuildKit secret for npm/Prisma TLS verification. It does not disable verification, persist proxy credentials, or bake the cloud CA into runtime trust. On an ordinary server, use the normal Compose build command. The helper writes Docker client metadata under /tmp when the home directory is read-only. It builds the same `hospital-kpi:local` image used by Compose; subsequently run `docker compose up -d --no-build`.

Turning demo seed flags off does not remove existing demo accounts or synthetic results. Use a clean production database, or create a real administrator first and explicitly disable all demo accounts before deployment. The last-administrator guard requires one active real administrator to remain.

For cloud builds, the helper can also fetch the exact pinned Prisma engine artifacts through the host's working proxy. It verifies each compressed artifact against the official vendor SHA-256 checksum over verified HTTPS, then supplies the public binaries through the optional `prisma_engines` BuildKit context. Standard builds use an empty scratch context and download normally. The pinned engine commit must be reviewed with any Prisma upgrade. Neither checksum validation nor TLS is disabled.
